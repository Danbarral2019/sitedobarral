# Onda 4.7 — Single-flight em `withCache`

**Data:** 2026-05-18
**Status:** Aprovado (design), implementação pendente
**Onda:** 4.7 (Saneamento 2026-05 — campanha de 6 ondas)
**Escopo final:** 2 PRs sequenciais em `main`. Refactor in-memory, sem distributed lock nesta onda.

---

## Contexto

`lib/cache/redis-client.ts` exporta `withCache(key, fn, ttl, options)`, usado em 24 call sites do projeto (incluindo `lib/ai/index.ts` para todas chamadas Gemini/Anthropic, `lib/embeddings/vector-search.ts` para busca semântica, e `app/api/documents/query/route.ts` para o chat RAG). O padrão atual é: `cache miss → executa fn() → setex(key, value, ttl)`. **Não há proteção contra cache stampede**: quando múltiplos requests batem na mesma key simultaneamente durante miss, todos executam `fn()` em paralelo, desperdiçando custo computacional (especialmente caro para chamadas LLM).

A Onda 4.7 introduz **single-flight de-duplication**: quando 2+ callers ativam `withCache` para a mesma key durante um miss, apenas o primeiro executa `fn()`; os demais aguardam a mesma Promise e compartilham o resultado. Implementação **in-memory por processo** (Map de promises), suficiente para o volume atual e o tipo predominante de stampede (refresh do mesmo user, mesma lambda warm).

## Achados do profiling (não há dataset/load test)

Diferente da Onda 4.6, esta onda **não** tem profiling prévio — é correção arquitetural profilática. Sinal indireto:

- 24 call sites usando `withCache`, dos quais ~3 disparam chamadas LLM caras (Gemini/Anthropic)
- Custo IA em prod tem componente fixo (token cost por chamada) que escala linear com número de chamadas redundantes
- Volume atual baixo (14 enrollments) mas cenários de stampede são plausíveis: newsletter blast → N alunos abrem mesma URL ao mesmo tempo; chat RAG → user aperta enter 2x rápido

## Arquitetura

**Único arquivo modificado:** `lib/cache/redis-client.ts`

- Adiciona constante de módulo `const inFlight = new Map<string, Promise<unknown>>()`
- Modifica `withCache` para consultar `inFlight` antes de executar `fn()`
- Estende `WithCacheOptions` com `singleFlight?: boolean` (default `true`)
- Adiciona `__resetInFlightForTesting()` exportado apenas para vitest (não usado em produção)

## API surface

```ts
export interface WithCacheOptions {
  /** Prefix for registry (enables prefix-based invalidation) */
  prefix?: string;

  /**
   * Default: true. Single-flight de-duplicates concurrent calls
   * for the same key within this process. When 2+ requests trigger
   * a cache miss for the same key simultaneously, only one runs `fn()`;
   * the others await the same Promise and share the result.
   *
   * Set to false to opt out (no known callers need this today).
   */
  singleFlight?: boolean;
}

export async function withCache<T>(
  key: string,
  fn: () => Promise<T>,
  ttl: number = CACHE_TTL.SEARCH_RESULTS,
  options?: WithCacheOptions,
): Promise<T>;

/** @internal — used only in tests */
export function __resetInFlightForTesting(): void;
```

**Assinatura inalterada.** 24 call sites continuam funcionando sem modificação.

## Data flow

### Caller único (sem stampede)
```
T0   getCache(key) → null
T1   inFlight.get(key) → undefined
T2   register promise, set Map
T3   fn() inicia
T800 fn() retorna, setCache(key, value, ttl)
T801 finally: inFlight.delete(key)
T802 retorna value
```
Latência: idêntica ao código atual. Overhead: microsegundos.

### Stampede de 3 callers (mesma key)
```
T0   A: getCache → null, inFlight.get → undefined, registra, fn() inicia
T5   B: getCache → null, inFlight.get → promise de A, AWAIT compartilhado
T8   C: getCache → null, inFlight.get → promise de A, AWAIT compartilhado
T800 fn() de A termina, setCache, delete inFlight, promise resolve
T801 A, B, C todos recebem value (mesmo objeto em memória)
```
**Custo: 1 execução de fn() em vez de 3.** Pra `lib/ai/index.ts` isso significa 1 chamada Gemini em vez de 3.

### Erro durante fn() compartilhada
```
T0   A: registra promise, fn() inicia
T5   B: AWAIT promise de A
T800 fn() lança → finally → inFlight.delete(key)
T801 A, B recebem mesmo erro original
T900 D chega: getCache → null, inFlight.get → undefined (já deletado),
     nova promise, executa fn() fresh
```
**Sem cache poisoning.** `setCache` só é chamado APÓS sucesso de `fn()`. Erro não persiste além da janela do stampede.

### Cold start (lambda nova)
`inFlight = new Map()` vazio. Comportamento idêntico ao caller único. Sem regressão.

### Cross-instance (2 lambdas warm + mesma key)
**Não coberto nesta onda.** Cada lambda tem seu próprio Map. Se 2 lambdas distintas recebem requests simultâneos pra mesma key, ambas executam `fn()` uma vez (mas dentro de cada uma, dedup funciona). Cobertura ~90-95% dos casos práticos. Upgrade para distributed lock (SETNX) pode ser feito em Onda futura se o volume crescer.

## Leak protection (PR 4.7.1)

```ts
const MAX_IN_FLIGHT = 1000;

function registerInFlight<T>(key: string, promise: Promise<T>): void {
  if (inFlight.size >= MAX_IN_FLIGHT) {
    if (Math.random() < 0.01) { // 1:100 sampling
      apiLogger.warn(
        { cache_in_flight_size: inFlight.size, max: MAX_IN_FLIGHT },
        'cache.single_flight.high_water_mark',
      );
      Sentry.captureMessage('cache.in_flight.exceeded_threshold', {
        level: 'warning',
        extra: { size: inFlight.size, max: MAX_IN_FLIGHT },
      });
    }
  }
  inFlight.set(key, promise);
}
```

**Decisões:**
- Não recusa registrar (correctness > defensive coding); apenas alerta
- Amostragem 1:100 pra evitar flood Sentry/logs em vazamento contínuo
- Sem eviction (LRU esconderia bugs; eviction silencioso quebra contrato single-flight)
- MAX = 1000 é "claramente algo deu errado" sem ser tão alto que demore pra detectar
- Memória: 1000 × ~200 bytes = ~200KB, desprezível

## Error handling

| Cenário | Comportamento |
|---|---|
| `fn()` lança | Todos awaiters recebem mesmo erro; Map limpa via `finally`; próxima request faz miss limpo |
| `setCache` falha (Redis 500) | Engolido + logado (comportamento atual mantido); fn() retornou OK → caller recebe o resultado |
| Redis indisponível (`redis === null`) | Bypass total: `withCache` chama `fn()` diretamente, sem single-flight |
| `getCache` falha | Tratado como miss (atual); single-flight ativa normalmente |
| Promise unhandled rejection | `finally` ainda roda, Map limpa; Node loga warning |

**Sem negative caching nesta onda.** Erros transitórios continuam sendo retried normalmente (comportamento idêntico ao hoje).

## Itens fora do escopo (documentados para depois)

- **Distributed lock (Redis SETNX)**: necessário se profiling pós-4.7 mostrar stampede cross-instance recorrente
- **Negative caching**: cachear erros transitórios por TTL curto (~5s) pra evitar retry hammering downstream
- **Métricas Sentry mais ricas**: contadores de dedup hits por key (high cardinality — avaliar custo)
- **TTL coordinator** (stale-while-revalidate): refresh assíncrono antes do TTL expirar, evitando miss simultâneo em renewal

## Riscos identificados

| Risco | Mitigação |
|---|---|
| Map leak por bug em `finally` | Cobertura de teste do error path + MAX_IN_FLIGHT warning em PR 4.7.1 |
| Falha cross-instance não detectada | Volume atual baixo; reavaliar se Sentry/Vercel logs sinalizarem stampede após 1-2 semanas |
| `singleFlight: false` esquecido por caller que precisa de side effects | Auditoria 2026-05-18 confirmou que NENHUM dos 24 callers atuais precisa; documentar a regra no JSDoc do helper |
| Promise compartilhada vaza dados sensíveis entre callers | Falsa preocupação: a key é deterministicamente derivada — dois callers compartilham promise somente se já fariam mesma query |
